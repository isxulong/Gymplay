# ADR-009 · HEVC 口径演进变更登记

- 状态：已定稿（2026-11-03 补记；登记的是 P9 探针结论落地后的口径演进）
- 依据：《综合方案修订定稿 v2》§1 需求映射（F1「本地导入（含 HEVC 引导）」）、§2.3（sources.ts「HEVC 预判引导」）、§2.6 错误文案映射表（R9）；M-1 P9 探针结论（ADR-001）；CHANGELOG [0.1.0]
- 登记性质：文档债批次补录，登记口径演进轨迹，使方案原文措辞与实现口径的差异可追溯。

## 口径演进轨迹

**阶段一 · 方案 v2 原文口径（2026-11-02 签发，措辞为「引导」）**

方案 v2 在三处使用「引导」类措辞，彼时 P9 未实测：

- §1 需求映射表 F1 行：**「本地导入（含 HEVC 引导）」**；
- §2.3 工程结构 `sources.ts` 注释：「视频源装载（仅 File API；**HEVC 预判引导**）」；
- §2.6 错误文案映射表：「HEVC 探测失败 → 『该视频为 HEVC 编码，当前浏览器不支持，请转 H.264 后导入』（R9 fallback）」。

「引导」隐含的预设是：HEVC 导入可能需要一步转码引导流程（预判 → 不支持则引导用户转码）。

**阶段二 · P9 探针结论（2026-11-02 实测，见 ADR-001 P9 行）**

P9 实测：目标设备可直读（hev1 / hvc1 双样本出画面出声）→ 结论为「M1 的 HEVC **不需转码引导，仅做提示**；R9 fallback 文案保留给不支持平台」。

**阶段三 · M1 起的实现口径（v0.1.0 落地）**

- `src/platform/sources.ts`：HEVC 文件按「直读」处理——平台探测可播则直接装载并带 `hevc-passthrough` 提示标记；**仅当**平台探测不支持 HEVC 时才走 R9 fallback 文案（`COPY_HEVC_UNSUPPORTED`，即方案 §2.6 原文）。无任何转码引导流程。
- CHANGELOG [0.1.0]：「本地文件装载（HEVC 直读提示，P9 结论）」。
- README：「iPhone 拍的 HEVC 视频在支持的浏览器上直接装载，无需转码」。

## 变更登记结论

1. **实现口径 = 「直读 + 提示 + 不支持时 R9 fallback 文案」**，与方案 v2 §1/§2.3 的「引导」类措辞存在表述差：方案措辞是 P9 实测前的预设写法，实测后被 P9 结论收窄，实现按收窄后口径落地、行为与方案 §2.6 的 R9 fallback 条款一致。
2. 该演进**不构成功能或契约变更**：R9 fallback 文案、触发条件（canPlayType 否定 / 平台探测不支持）均与方案 §2.6 一字未改；变化的只是「支持 HEVC 的平台」从设想的引导流程简化为直读。
3. 方案 v2 原文如需回写，改法建议：F1 行「含 HEVC 引导」→「含 HEVC 直读提示」、§2.3「HEVC 预判引导」→「HEVC 预判 + 不支持时 R9 fallback」；属措辞对齐，无条款实质变化。
