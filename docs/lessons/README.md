## 收录标准

三条**缺一不收**：

1. **自带可跑的东西**——一条能在当前树原样执行的命令（含期望退出码或输出锚点），或一个能 `grep` 到的源码位置。
2. **真实发生过**——点名它防的**一类**事故，并给出该类事故在本仓库发生过一次的位置（日志章节或 `文件:行`）。
3. **违反默认做法**——一个做了十年的人本来就那么做的事，不值得写。写下来只是常识的复读。

## 不收录

- **架构决策**（归 `docs/adr/`）。判法：改写为「我们选 X 不选 Y，因为 Z」读得通 → 归 ADR。
- **`scripts/*.mjs` 头注已有的机器规则**。权威在脚本（与代码同版本演进），文档再抄一遍，下次脚本重构后就成了假权威。
- **实跑流水**（tsc / vitest / 门禁表格、CI 运行号）——必然过期的快照。
- **命令速查表**——`README` 与脚本头注已有；两边写必然分叉。
- **脱离构造条件的单点数值**——三年后没人能重建，后来者还会把它当"当前值"引用。
- **发布前未验证清单**——属发布说明；写进这里等于把"没做完的事"固化成长期条目。
- **纪律口号**——「要有责任心」「加强沟通」「重视质量」这类不可判定的表述，一句都不收。

## 维护规则

1. **上限是硬的**：新条目想进来，必须先挤掉一条，或论证某条已失效。只增不减会让这份文档变成垃圾场。
2. **提交前把引用的位置 grep 一遍**。本仓库曾两次写出指向不存在对象的引用（`bench-4c.mjs` 不存在、日志「第 6 次追加」不存在），修复动作本身又造出新的悬空引用——见 EXP-003。
3. **引用的行号会漂移**，所以每条同时记原文与替换文本，不只记行号。

## 与验证日志的关系

每条指向 v0.3.3 验证日志的章节与行号。冲突时**以能在当前树跑出结果的一方为准**——日志是当时的记录，可能记错；代码与命令是事实。

日志中已确认记错的两处，本文档不予沿用：

- 日志把「`grep` 统计 `+++ b/` 得 0 行」归因为「中文 UTF-8 多字节序列」。该补丁 0 个 NUL 字节、严格 UTF-8 可解，且同一文件现用裸 `grep` 能正常输出 30 行——归因不成立。真正可重建的机制是 NUL 字节触发的二进制判定，与中文、文件大小、挂载点均无关（见 EXP-005 其二）。
- 日志「2px / 0px / 15px」三个数字的往返，是取数层级不统一的后果（页面级 0px、容器级 15px 同时为真），不是三次独立的错误（见 EXP-005 末段）。
