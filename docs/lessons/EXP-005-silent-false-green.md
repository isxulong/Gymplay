# EXP-005 · 静默假绿：成功信号不是正确结论

- 状态：现行｜起始 v0.3.3（2026-11-06）

## 背景

四起事故，共性是「命令没报错，结论是错的」。共同点：**检查手段本身失效了，而失效信号长得像成功**。

### 其一：管道吞掉退出码

```bash
git push origin main | tail -6   # 看着成功，$? 是 tail 的退出码
```

实测同一动作三种写法：

```bash
bash -c 'exit 1' | tail -1; echo $?               # 0  ← 假绿
bash -c 'exit 1' > /tmp/p.log 2>&1; echo $?       # 1  ← 真
bash -c 'exit 1' | tail -1; echo ${PIPESTATUS[0]} # 1  ← 真
```

本仓库真实发生过：一次 `git push` 返回 `502`（远端瞬时故障），因为接了管道，被记成成功。

### 其二：裸 `grep` 遇二进制文件把命丢进 stderr

`grep` 判定文件为二进制后，**裸 `grep`（不带 `-c`/`-l`/`-a`）会把 `binary file matches` 写到 stderr、stdout 一个字节都不给，而退出码仍是 0**。于是 `grep … | wc -l` 得到 0，被读成「文件里没有这些行」。

本仓库真实发生过：统计补丁文件里 `+++ b/` 的行数得到 0 行，当时归因为「中文 UTF-8 多字节序列」。

**「中文导致的」这个归因是假的**，有两个独立证据：一是该补丁 0 个 NUL 字节、严格 UTF-8 可解（`d.count(b'\x00')==0`、`d.decode('utf-8')` 通过）；二是**同一份文件在当前环境下用裸 `grep` 能正常输出 30 行**（`grep -c '^+++ b/'` → 30，`rc=0`，stderr 空），逐挂载点、逐大小都一样。所以那次「0 行」的触发条件**今天已无法重建**，不能反过来断言它是 A 或 B 造成的。

**能重建的机制是 NUL 字节，与文件大小、挂载点、语言都无关**（GNU grep 3.7 实测）：

```bash
python3 -c "open('/tmp/b.dat','wb').write(b'\x00'*20000 + b'NEEDLE\n')"

grep "NEEDLE" /tmp/b.dat > /tmp/o.txt 2>/tmp/e.txt
# rc=0，stdout 0 字节，stderr = "binary file matches"   ← 假绿就在这里

grep "NEEDLE" /tmp/b.dat | wc -l        # 0        ← 被读成「没有」
grep -c "NEEDLE" /tmp/b.dat             # 1        ← -c 照样给数（stderr 仍提示）
grep -a -c "NEEDLE" /tmp/b.dat          # 1        ← -a 当文本处理
```

对照：同样 279,045 B 的纯文本（无 NUL）裸 `grep` 输出正常，`98,304 / 102,400 / 279,045 B` 三档都一样正常——**大小不构成阈值**。

### 其三：取数层级决定结论，而两个数字都能自证

量横向溢出时，`documentElement` / `body` / `#app` 三层都是 **0px**，`main` 容器层是 **15px**（client 343 / scroll 358）。日志第 13 节先记「2px」、复核二实测「0px」，两个都被当成「实测过」，结论却相反；主 AD 第 19 节因无独立复现而未选边。四级层同时量之后才定论：页面级 0px 成立、容器级 15px 也成立，**两个数字都对，只是量的是不同的层级**。

**做结论前先固定层级**：写清「量的是哪一层、该层该不该有溢出」。

### 其四：把「工具没输出」读成「文件里没有」

同一模式在别处复现：工具没输出 + `rc=0`，脚本与门禁都不报警，错误结论**静默通过**整条流水线。

## 做法

### 1. 退出码一律取自被检对象本身

```bash
# 不接管道，写文件再判断
cmd > /tmp/log 2>&1; echo "exit=$?"

# 必须接管道时，取缺失的第一段
cmd | tail -5; echo "exit=${PIPESTATUS[0]}"

# 多步命令
set -o pipefail
```

`PIPESTATUS` 是 bash 专有；zsh 用 `pipestatus`（小写、数组下标从 1 起）。

### 2. `grep` 结论前先分清「零命中」与「未检索」

```bash
grep -rn --include='*.ts' -a "关键词" src/; echo "rc=$?"
```

- `rc=1` 且无输出 → 真的没有。
- `rc=0` 且输出为空 → **被跳过了**，不是没有。换 `-a`、加 `--include` 限定范围，或改用 `rg`。

### 3. 凡「成功」要进结论，回读产物本身

文件内容、线上响应、数据库行——不看退出码，也不看工具自述。

### 4. 报告里分三档，第三档不许写成前两档

- **通过**：`rc=0` **且**回读到预期内容
- **未通过**：`rc≠0`
- **未验证**：工具行为不明 / 环境不支持 / 无法回读

## 后果

- **假绿进交付**：失败被记成成功，下游据此继续叠加改动，故障点离现场越来越远。
- **「无命中」当证据**：漏检被写成「确认不存在」，后来者照同一命令重跑仍然漏，形成稳定的错误共识。
- **复核失效**：复核人看到绿勾就不再深查，整条证据链最后只剩自述。
- **量错层级得出相反结论**：两个人都「实测过」，都「有数字」，然后互相指责对方编造。

## 边界

- `grep -a` 会把二进制当文本，可能产生乱码命中——需配合 `--include` 或 `rg` 限定范围。
- 本条只覆盖**本地命令层**的退出码语义；CI 流水线内各步骤的退出码如何传递未取证。
- 「回读产物」在只读环境里可能做不到（如第三方系统），那就如实归入「未验证」，不要降级成「通过」。
